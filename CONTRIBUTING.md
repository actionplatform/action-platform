# Contributing to Action Platform

Thanks for your interest in contributing.

There are many ways to help:

- Answer questions in GitHub Discussions
- Report reproducible bugs
- Submit pull requests that fix issues
- Add templates, cloud overlays or services to [actionplatform/templates](https://github.com/actionplatform/templates)
- Improve the documentation under `docs/`

Action Platform is a web app, a CLI and an MCP server on one Python core, maintained by a very small team. Contributions are welcome — but **alignment matters more than quantity**.

This guide explains what kind of contributions are likely to be accepted and how to submit them. Following it saves time for you and for the maintainers.

> [!IMPORTANT]
> These guidelines may feel stricter than in many open-source projects. That is intentional. Clear structure and boundaries keep the project sustainable and prevent maintainer burnout.

## High-level expectations

- Action Platform has a clear product direction: one core, three doors (web, CLI, MCP), git-flow enforced everywhere.
- Ownership and decisions are centralized.
- Review capacity is limited.
- Not every contribution will be accepted — even if technically correct.

## State of the project

The platform is pre-1.0. The web app, the API and the CLI are versioned and released independently (`web/vX.Y.Z`, `api/vX.Y.Z`, `vX.Y.Z`); breaking changes still happen between minors. Fixes and small improvements are accepted directly; new features and larger changes need prior discussion.

## What makes a strong contribution

### One pull request = one logical change

If your change is small and obvious (typo, narrowly scoped bug, small docs update), open a pull request directly.

If you are fixing a bug in `registry.py`, do not:

- reformat unrelated files
- refactor unrelated code
- fix style issues elsewhere
- combine multiple unrelated changes

Even "improvements" increase review complexity. Cleanups and refactors go in separate pull requests, after discussion.

### Code quality

- Python: `ruff check` and `ruff format` must pass; type hints on public functions.
- Web (`apps/web`): `npx tsc --noEmit` must pass; the design system is monochrome — use `components/ui/*`, never native `confirm`/`prompt`/`alert`.
- **No comments in source code.** Names explain the how; `docs/` explains the why. A change that needs explaining gets a paragraph in the relevant `docs/*.md`, not an inline comment.
- Every behaviour change ships with a test. Tests are `unittest.TestCase` classes under `tests/`, laid out like the package (`tests/core/flow/test_git.py` covers `action_platform/core/flow/git.py`). See [Development](docs/contribute_development.md).
- Nothing reaches a code host, a cloud or the network in tests; use the builders in `tests/support.py`.

## Discussion is required for larger changes

For anything beyond a small fix, discuss it before opening a pull request. This includes:

- new features
- UI/UX changes
- changes to default behaviour
- refactors or cleanup work
- new providers (source hosts, deploy targets)
- changes touching many files or several of the repositories in the ecosystem

Discussion happens in [GitHub Discussions](https://github.com/actionplatform/action-platform/discussions). Pull requests introducing major changes without prior discussion will be closed without review.

## What this project is not

- Not optimized for first-time open-source contributors; there are no mentorship issues.
- Large unsolicited changes are unlikely to be accepted.
- Broad refactors, style rewrites and "modernization" pull requests are not helpful.
- Low-effort AI-generated pull requests will be closed.

AI usage is allowed. Contributors must fully understand what their changes do and why.

# Ways to contribute

## 1. Support

Use GitHub Discussions. When asking for help, provide complete information: platform version (Settings shows the API version; `action-platform --version` for the CLI), logs, screenshots, steps to reproduce. Support is voluntary — do not ping people for attention.

When helping others: verify before you answer, be patient, remember that experience levels differ.

## 2. Bug reports

Create a GitHub issue only if the bug is reproducible and no existing issue covers it. A report must include:

- clear reproduction steps
- expected result
- actual result
- versions: CLI, API and web (Settings → API), the code host involved, how the platform is deployed (`install.sh`, Dokploy, compose)

Incomplete reports and reports generated by AI without verification may be closed.

## 3. Code

Maintainers may close pull requests at their discretion, without explanation.

### Issue requirement

Every pull request should reference and close an issue or a discussion. If none exists, create one first. Pull requests without a linked issue or discussion may not be reviewed.

### Branches follow git-flow

This repository runs on the same rules it enforces for everyone else. Branch from `master` as `<kind>/<code>[-slug]` where `kind` is one of `feature`, `bugfix`, `hotfix`, `chore`, `docs`, `refactor`, `test`, `ci`, `perf` and `code` is the issue number:

```
feature/42-template-sources
bugfix/57-symlink-workspaces
docs/12-contributing
```

The git hooks refuse anything else (`action-platform install` puts them in place; `action-platform branch feature 42` creates the branch for you). Pull requests target `master`.

### Commit message format

[Conventional Commits](https://www.conventionalcommits.org), in English:

```
fix(api): refuse repositories whose symlinks escape the workspace
feat(web): repository owner per source host
docs: template repositories per organization
test: unittest classes mirroring the package layout
```

Scopes in use: `api`, `web`, `cli`, `mcp`, `core`, `templates`, `deploy`, `ci`. Keep the subject under 72 characters; use the body only for a one-sentence *why*. Walls of text listing every change will be rejected — the diff already says what changed.

### Pull request title format

Same as the commit format: `fix(api): …`, `feat(web): …`. The description lists what changed and how it was tested.

### AI usage disclosure

If AI tools were used at any stage, say so in the pull request description. AI is allowed; you must understand every change, verify it, and make sure it follows the project's patterns. Pull requests that look generated without understanding will be closed.

### Test before submitting

Before opening a pull request:

- `poetry run ruff check . && poetry run ruff format --check .`
- `poetry run pytest -q`
- for web changes: `cd apps/web && npx tsc --noEmit`, and the flow exercised in a browser
- provide the testing steps in the pull request description

CI runs code quality, Conventional Commits, git-flow and Trivy on every pull request; all four must pass.

### Where things live

| Change | Repository |
|---|---|
| CLI, API, web app, MCP server, docs | this repository |
| project templates, cloud overlays, services | [templates](https://github.com/actionplatform/templates) |
| the one implementation of setup / check / release / commit lint used by every generated project | [ci-scripts](https://github.com/actionplatform/ci-scripts) |
| thin wrappers per CI | [ci-github](https://github.com/actionplatform/ci-github), [ci-gitlab](https://github.com/actionplatform/ci-gitlab), [ci-jenkins](https://github.com/actionplatform/ci-jenkins) |

A change to a template or a CI script becomes visible to every generated project when `v1` moves — it needs the same care as a change here.

## FAQ

**Should I ask before fixing a typo or a small bug?**
No. Small, obvious fixes can be submitted directly.

**I have an idea for a new feature.**
Discuss it first in GitHub Discussions. Do not open a pull request for a new feature without prior alignment.

**Can I work on an open issue?**
Comment on the issue first to confirm it is still relevant and nobody else is on it. For anything beyond a small fix, describe your approach before implementing.

**I noticed code that could be cleaned up while working on my change.**
Stay on your stated goal. Cleanups go in a separate pull request, after discussion.

**Can I use AI to help with my pull request?**
Yes. You must fully understand and verify the changes, and disclose the usage.

**My pull request was closed without detailed feedback.**
It usually means the change did not match the project's direction or needed more review bandwidth than available. A closure is feedback, not a rejection of your effort — address it before opening a new one; repeating the same approach hurts your standing with maintainers.
