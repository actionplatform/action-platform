# API

`action-platform-api serve` — the JSON API the web app drives; a FastAPI process listening on `:7788` with OpenAPI at `/docs`. It is released as its own component (`api/vX.Y.Z`, image `actionplatformio/action-platform-api`) and reports that version in `GET /api/version`.

`action-platform-api serve` — one process that refuses to start without `AP_DATABASE_URL`. The API keeps no state on disk. What the app pages read — detail, git-flow health, commits, branches, tags, releases, manifest — comes from `app_snapshot`, a row stored after every change the platform makes (sync, release, push, branch, checkout, commit, configuration) and on first sight; `GET` routes never touch git. A sync reads the remote's refs with `git ls-remote` and the commits, files and tags from the code host's API, and falls back to a clone only when the host cannot answer; requests that change something still clone fresh (a disposable clone under `AP_WORKSPACES`, brought level with the remote at most every `AP_WORKSPACE_TTL` seconds), apply the app's pending edits from the database and work there. Accounts, sessions, organizations, apps, pending edits and tokens live in the [database](concept_database.md) the API owns. Which organization, project or app a caller may touch is decided here too: `/api/v1/*` is the same API behind a gate that knows who is calling.

Clients call them under the app's project, `/api/v1/projects/{project}/apps/{app}/…` (`{app}` is the app's id or its registry id, and `-` in place of `{project}` stands for the project of that registry id): `GET …/apps/{app}`, `…/gitflow`, `…/commits`, `…/branches`, `…/tags`, `…/versions` (the releases tagged in the clone; `…/releases` is the paged list imported from the code host), `…/changes`, `…/next-version`, `…/branches/plan`, `…/manifest`, `POST …/sync`, `…/push`, `…/release`, `…/deploy`, `…/branches`, `…/checkout`, `…/pull-request`, `…/manifest/export`, `…/services`, `…/install`, `…/discard`, `…/commit`, `PUT …/manifest`, `…/cloud`, `GET …/diagnose`, and `GET /api/v1/projects/{project}/apps` for the registry rows of a project (`-` for every project the caller reaches). `/api/apps/*` and `/api/v1/apps/*` still answer the same way, marked deprecated in the schema and with a `Deprecation: true` header on every answer.

## Auth

`/api/auth/*` is where accounts live; the web app is a client of it and sets the browser cookie the API signs.

| Endpoint | |
|---|---|
| `GET /api/auth/status` | `{configured, users, organizations, password_recovery, google, setup}` — whether `AP_AUTH_SECRET` is set, how many accounts and organizations exist, which sign-in options are on, and `setup`: `open` until the first account exists, then `closed` |
| `POST /api/auth/sign-up {name, email, password, invitation_id, setup_token}` | the first account needs `setup_token` (`action-platform-api setup token`; `403 setup_token` without it); afterwards needs a pending invitation for that email (an invitation bound to a code-host login takes any email). Answers user + session (`token`, signed `cookie`, `expires_at`) |
| `GET /api/auth/invitations/{id}`, `POST /invitations/{id}/accept` | open an invitation (`email`, or `login` and `host_kind` when it is bound to a code-host login; role, organization, status) and accept it as the signed-in user, who joins with its role and the teams it carries. A login invitation refuses the plain accept |
| `POST /api/auth/invitations/{id}/verify {origin}`, `POST /invitations/{id}/verify/callback {origin, code, state}` | accept a login invitation: `verify` answers the code host's sign-in URL (the platform's OAuth app for that host, asking only for the profile); the callback trades the code for the login and joins when it is the invited one |
| `POST /api/auth/sign-in {email, password, ip_address, user_agent}`, `POST /sign-out` | password checked with the same scrypt parameters the web app used, so every existing account keeps working; 10 attempts per minute per IP |
| `GET /api/auth/session` | who the caller is: user, session, active organization, every organization, role and its grants. The caller identifies with `X-Session-Token` (raw) or `X-Session-Cookie` (the signed cookie value) |
| `POST /api/auth/session/organization {organization_id}`, `GET /sessions`, `DELETE /sessions/{id}` | switch organization (members only), list and revoke browser sessions |
| `POST /api/auth/organizations {name, slug, git_author_name, git_author_email}`, `POST /members {organization_id, name, email, password, role}` | create an organization (caller becomes owner, it becomes active); add a member with a password (owners and admins) |
| `POST /api/auth/password/change {current_password, new_password}` | the caller's own password, `204`; `400 wrong_password` for a wrong current one and `400 weak_password` under 8 characters, both change nothing. Keeps the calling session, ends every other session and revokes every API token of the account, so the CLI and MCP log in again; 5 attempts per minute per IP |
| `POST /api/auth/password/forgot {email}`, `POST /password/reset {token, password}` | the emailed-link flow. `forgot` answers `202` whether or not the address has a password account (5 attempts per minute per IP) and sends a single-use link valid for 30 minutes to `<public url>/reset-password?token=`; `503` while `AP_SMTP_HOST` is not set. `reset` answers `204` and sets the password, ends every session and revokes every API token of the account; `400 invalid_token` for an unknown, used or expired token and `400 weak_password` under 8 characters; 10 attempts per minute per IP |
| `POST /api/auth/google/start {origin, next}`, `POST /google/callback {origin, code, state, verifier, ip_address, user_agent}` | sign in with Google when `AP_GOOGLE_CLIENT_ID` and `AP_GOOGLE_CLIENT_SECRET` are set (`404` otherwise; `GET /api/auth/status` reports it as `google`). `start` answers `{url, verifier}`: Google's authorize URL (PKCE, the `state` signed by the API) and the verifier the web app keeps until the browser returns; `callback` trades the code for a verified email and answers user + session like `sign-in`, plus `next`, the path to open (`/invite/<id>` when the email has a pending invitation). 20 attempts per minute per IP |
| `POST /api/auth/device/code {client_id, scope}`, `POST /device/token {grant_type, device_code}` | RFC 8628 for the CLI: `authorization_pending`, `slow_down`, `access_denied`, `expired_token` as `{error, error_description}`; an approved code becomes a session token |
| `GET /api/auth/device?user_code=`, `POST /device/approve {user_code, grant}`, `POST /device/deny` | the browser side: what the device asked, then approve with a grant cut to the caller's role, or deny |
| `POST /api/auth/tokens {name, scope, organization_id, project_id, app_id}` (the one place tokens are minted, also for the CLI's login; `POST /api/v1/tokens` answers as a deprecated alias), `GET /tokens`, `DELETE /tokens/{id}`, `POST /tokens/verify {token, client}` | scoped JWTs ([access control](concept_access_control.md)); `organization_id` `*` reaches every organization; `verify` answers the claims plus organizations and role, and records the client program |

Sessions last 7 days, refreshed when used after a day. Refusals answer `{"detail", "error", "error_description"}` with `401` (`unauthenticated`, `invalid_credentials`), `403` (`forbidden`, or `disabled` for an account an operator disabled with `action-platform-api users disable`: no sign-in, its sessions and tokens refused), `409` (`exists`), `429` (rate limit) or `400` for the rest.

Every response is typed and published as OpenAPI at `/docs`; the web app generates its client from that schema. Requests that touch a source host reach the route with `credentials {kind, token, username, base_url, owner, author_name, author_email}`, added by the gate from the database — no client sends them; identity alone is valid for a local commit.

## Trust

Every route but `/api/version`, `/api/health`, `/docs`, `/redoc`, `/openapi.json` and the two `/.well-known/` documents requires `Authorization: Bearer <AP_API_TOKEN>`, the API's shared secret (the web app does not send it: it calls `/api/v1` and `/api/auth` with the session), checked in constant time. Without a token the API refuses to start — `AP_ALLOW_UNAUTHENTICATED=1` opts into an open API for local development only. Two prefixes authenticate the person instead: `/api/auth/*` (sessions, tokens, the device flow) and `/api/v1/*`, the user-facing face of the same routes. The web app rewrites both paths to the API unchanged — release tags with dots in them included — so the CLI, MCP and browser reach them through the platform's public address.

## Instance health

`GET /api/health` needs no token: `200` or `503` with `{status, database, migrations, workers: {light, deploy}}` — database reachable, migrations at head, a worker seen in the last minute for each kind group. `GET /api/v1/instance/health` (owners) adds `workers_seen` (name, kinds, times, `alive`), the `queue` per kind for the caller's organization (`queued`, `running`, `oldest_queued_seconds`, `worker_running`), `integrations` (`smtp`, `google` with the `redirect_uri`, `sentry_api`, `oauth_apps`) and the versions; `POST /api/v1/instance/test-email` (owners) sends to the caller and answers `{sent, to, error}`. [Observability](concept_observability.md#instance-health) has the details.

## `/api/v1`

A gate sits in front of `/api/v1/*` and, for every call:

- identifies the caller — a token from `action-platform login`, a session token or the browser cookie;
- finds the app's organization and checks the caller's role there against the route's permission, the token's scope against the same permission, and the token's reach (one project, one app). A token spanning every organization names one with `X-Organization: <id or slug>` on organization-level routes;
- fills in what the workspace needs from the database: the source host's credentials (refreshed through the OAuth app when expired), the organization's commit identity, the template repositories it added;
- after `sync`, `release`, `push`, `branches`, `checkout`, `pull-request` and `commit`, copies releases and pull requests from the source host into the database;
- cuts `GET /apps` to the apps the caller may see.

Routes that are not workspaces live directly under `/api/v1` and are what the web app's pages and server actions call:

`GET plugins` lists the plugins the image carries — name, version, the options each declares (`key`, `label`, `kind`, `help`, `required`) and a load error when there is one (a plugin with the reserved slug `access` is refused there); `GET/PUT plugins/{slug}/options` read and replace the organization's values for them (`org.manage`; a slug the image does not run is a `404`, since only a loaded plugin says which keys are secrets to seal) — every deploy job carries them to the target as `AP_<SLUG>_<KEY>`. An organization without options of its own reads the platform's only when `AP_PLATFORM_CONNECTIONS` grants it ([options](use_plugins.md#options)). Nothing installs, removes or restarts at runtime: a plugin joins the platform as a dependency of the image.

`GET hosts/{id}/access` asks the provider what the connected account may create with (GitHub App installations and their permissions, GitLab groups, Bitbucket workspaces) and names what is wrong. The OAuth routes hold the whole dance: `start` answers the provider's authorize URL with a signed state, the browser comes back to the web app's `/api/oauth/{provider}/callback`, which hands code and state to `callback`; the API exchanges the code, reads the account and stores the host. The same routes connect a service that is not a code host (`sentry`): the grant is stored as the organization's connection of that kind, listed by `GET connections` (kind, login, scopes granted, scopes asked, `missing`, expiry — never a token). Connecting asks the provider for the platform's scopes plus those the enabled plugins declare in `connections`. `POST /api/auth/invitations/{id}/accept` and the public `GET /api/auth/invitations/{id}` complete the invitation flow. A token limited to a project or app is refused on every management route.

`AP_<PROVIDER>_CLIENT_ID` / `_CLIENT_SECRET` (or the web app's `GITHUB_CLIENT_ID`… names) let the API refresh expired OAuth tokens; without them a host connected through OAuth keeps working until its token expires.

## Workspaces

The registry — id, name, url, default branch of every app — is the `registry` table, so every API instance and worker sees the same apps. An `apps.json` under `AP_HOME` from versions before 0.6 is imported once on boot, ids kept, and renamed `apps.json.imported`. Each instance keeps its clones under `AP_HOME/workspaces/<id>` (`~/.action-platform`, `/data/action-platform` in the image) and clones an app again when it is asked for one it does not have; a private repository needs credentials for that, which every mutating call carries, so a fresh instance rebuilds on the first `sync`. Every call that opens a workspace brings `platform.toml` back when it is missing, so an app never errors for something the platform can fix itself.

## Jobs

Every `POST /api/v1/apps/{id}/sync|push`, and every `release` or `deploy` that is not a dry run, is a job: the call answers `202 {job, status, poll}` and a worker (`action-platform-api worker`) runs it with the same services, filling in credentials and identity and copying releases and pull requests afterwards. There is no inline variant and no header that asks for one; a `release` or `deploy` with `dry_run: true` (the default) is a preview, answers inline and leaves no job. A `deploy` to a stage that already has one queued or running is refused with `409` (one deploy per environment). `GET /api/v1/jobs/{id}` answers `status` (`queued` → `running` → `done` | `failed`), `no_worker` (true for a job queued more than two minutes with no live worker taking its kind), `attempts`, `result` (the action's answer: the deploy results, the release preview, the synced app) and `error`; `GET /api/v1/jobs?app=<registry id>` lists an app's last twenty. A second `sync` for the same app while one is live returns the live job. Failures retry three times with backoff; a job whose worker vanished goes back to the queue after thirty minutes. The worker writes each target's deployment as `running` before it starts or follows anything, and finishes it as `success` or `failure`. The remote MCP server (`action-platform mcp --remote`) follows the job until it ends and answers with its result; one still running after fifteen minutes answers with the job, to follow with `job_status` and `job_logs`.

## Adoption

`POST /api/v1/projects/{id}/install` installs the platform on many apps of a project at once, on the worker:

```json
{"apps": ["<app id>", "<app id>"], "type": "web", "ci": null, "language": null, "code": "platform", "dry_run": true}
```

`apps` empty means every app of the project the caller reaches; `ci` and `language` empty mean detected per repository (`language: "none"` installs without the quality config); `dry_run` defaults to `true`. The answer is `202 {job, poll}`. The job clones each repository and, from its base branch (`develop` when it exists, else the default branch), runs the installer: a dry run answers the plan, otherwise the files are committed on `chore/<code>` and a pull request is opened against the base, and the app moves to that branch. `GET /api/v1/jobs/{id}` ends with `{dry_run, branch, apps, opened, skipped, failed}`; each entry of `apps` is `{app_id, name, state, skipped, reason, pull_request, plan}`, `plan` being `{type, language, ci, detected_ci, created, kept, warnings, version, version_source, base, branch}` with `version` the one `LAST_VERSION` starts at and `version_source` where it comes from, as the installer says it: the release tag, the manifest that declares it, the CHANGELOG, or `LAST_VERSION` when the file already exists.

Each app runs on its own, so one failure never stops the others; `reason` names it — `archived: the repository is read-only`, `no permission: …` with the host's words, `unknown language: …`, or a `chore/<code>` branch that exists with no open install pull request. A second run opens nothing twice: an app whose base branch has `platform.toml` is `installed` and skipped, one whose install pull request is still open (opened by an earlier run, or reported open by the code host from `chore/<code>`) is `pr_open` and skipped. Only one non-dry run per project is live at a time: a second one answers the job already queued or running.

`GET /api/v1/projects/{id}/adoption` answers one row per app — `{app_id, name, registry_id, state, reason, language, ci, version, branch, pull_request, checked_at}` — with `state` `unchecked` (no run has looked at it), `missing` (no `platform.toml`), `pr_open`, `installed` or `failed`, as the last run found it. A `pr_open` whose pull request the code host reports merged reads as `installed`, closed as `missing`.

## Job logs

`GET /api/v1/jobs/{id}/logs?after=<seq>&limit=<n>` answers what the worker wrote for a job — the core's log records, a plugin's `sam build` / `sam deploy` output line by line — as `{lines: [{seq, at, line}], next, status, kind, no_worker, finished}`. Lines are stored as they happen (flushed every half second or fifty lines); poll with `after=next` until `finished` is true. Same visibility as `GET jobs/{id}`: a member of the job's organization. A job keeps at most twenty thousand lines; a longer output ends with a truncation notice.

## Errors

`ActionPlatformError` and its subclasses (`ReleaseError`, `BranchError`, `PullRequestError`, `SyncError`, `TemplateError`, `InstallError`) answer `400 {"detail": "…"}` with a message meant for the user; `HTTPException` carries `404`, `409`, `410` and `422` (`{"code": "needs_install"}` when a repository has no `platform.toml`). Anything else is a `500` and reaches Sentry when `AP_SENTRY_DSN` is set ([observability](concept_observability.md)).

## Identity

`GET /.well-known/openid-configuration` and `GET /.well-known/jwks.json` are open; `POST /api/v1/identity/token` (`audience`, optional `project_id`, `app_id`) answers a five-minute RS256 token for a caller with `app.release` — see [identity](concept_identity.md).


## Pages

Lists that grow are paged on the API: `GET /api/v1/projects/{p}/apps/{a}/releases`, `…/pull-requests`, `…/ci` and `GET /api/v1/jobs?app=<registry id>&kinds=deploy,destroy` take `page` (from 1) and `per` (1–100, default 10) and answer with `items` (or `runs`), `total`, `page` and `per`. The web tables keep the page and size in the URL (`?page=2&per=25`) and ask the API for that slice; nothing is paged in the browser.


## Webhooks

`POST /api/webhooks/{host_id}` (the web app forwards it to `POST /api/v1/webhooks/{host_id}`) takes the code host's deliveries. No session: the request is verified against the host's secret — GitHub `X-Hub-Signature-256`, Bitbucket `X-Hub-Signature` (HMAC-SHA256 of the body), GitLab `X-Gitlab-Token`. A delivery whose repository matches an app of the host's organization queues one `sync` job for it (deduplicated while one is live); other events and repositories answer `202` with nothing queued. `GET`/`POST /api/v1/hosts/{id}/webhook` read the URL and rotate the secret (`org.manage`).

`POST /api/webhooks/github-app` (forwarded to `POST /api/v1/webhooks/github-app`) takes the deliveries of the platform's GitHub App: one URL for every installation, verified against the secret GitHub generated when the App was created from the manifest. The repository finds the apps on a GitHub host in every organization that tracks it, and each gets one `sync` job; without a stored secret it answers `404`. `GET`/`POST /api/v1/oauth/apps/github/webhook` read that URL and generate a new secret for an App created before the manifest carried one (`org.manage`).


## Readiness

A release carries, per stage, whether it can be deployed there. `GET projects/{p}/apps/{a}/releases/{tag}/readiness` answers one row per stage — `stage`, `status` (`queued`, `running`, `done`), `verdict` (`ok`, `blocked`, `pending`), `ok`, `checks[]`, `job_id`, `checked_at` — each check with `id`, `ok`, `level` (`static`, `target`), `severity` (`error` blocks, `warning` does not), `detail`, `fix` and the `target` it came from. `POST` the same path with `{stage}` (or `{}` for both stages) queues a `readiness` job per stage — deduplicated per release and stage while one is live — and answers `{jobs, readiness}`. The releases page (`GET …/releases`) carries `readiness: {dev: "ok", prod: "blocked"}` on every row. The worker queues the checks itself after `POST apps/{id}/release`. The model and the checks: [deployments › readiness](concept_deployments.md#readiness).

## Insights

`GET /api/v1/dashboard` — the organization's day (deployments and CI runs by status today, releases this week, apps without CI, the latest events across apps), narrowed to the token's project or app, cached thirty seconds; `?fresh=true` recomputes. `in_progress` lists the deployments still `queued` or `running`, latest started first, and is never cached. `GET /api/v1/projects/{p}/apps/{a}/activity?kind&limit` — one app's events, newest first, not cached: `kind` is `release`, `deployment`, `ci_run` or `pull_request` (any other answers `400`, none means all four), `limit` 1–100, default 50; each event has the dashboard's fields. `GET /api/v1/projects/{p}/apps/{a}/releases/{tag}/timeline` — one release with the pull requests merged since the previous tag of the same component, the CI runs on the tag (by ref or sha) and the deployments that reference it.
