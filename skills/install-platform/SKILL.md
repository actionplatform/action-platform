# Installing the platform in an existing repo

For repositories that were not generated by `init_project`.

1. `install_platform` (dry run by default). It detects the language from `pyproject.toml`, `go.mod`, `package.json`, `composer.json`, `pom.xml` or `Cargo.toml`; pass `language` when detection fails and `type` when the project is not a web service.
2. Show `created` and `kept`. Nothing that exists is overwritten: an existing `code-quality.yml` or `.code_quality/` stays as is.
3. On approval, `install_platform` with `dry_run=false`. Hooks go into `.git/hooks` (unversioned) — re-run `install_hooks` after upgrading the CLI; nothing to commit for that.
4. Warn what changes for the team from that moment: commits must be Conventional Commits, work must happen on `<kind>/<code>` branches, `main`/`develop` refuse direct commits. If the repo used another commit style, say so before flipping the switch.
5. The new files are uncommitted. Platform files may be committed straight on the default branch as `chore(platform): install action-platform` — one of the three exceptions the hooks allow (`chore(release):`, `chore(platform):`, `chore: bootstrap`). Then `gitflow_audit`.

Deploy is untouched: `[deploy]` is not written. Use the add-cloud skill only if the user wants the platform's overlay instead of their own pipeline.
